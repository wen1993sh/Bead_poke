# 拼豆色号数量汇总统计器设计说明

## 目标

做一个本地网页工具，用来读取一个固定文件夹中的宝可梦图鉴素材，先自动从图片里生成每个条目的 JSON，再把条目以图鉴卡片形式展示出来，让用户勾选想要拼的宝可梦，最后自动汇总所需的拼豆色号和数量。

这个工具的重点是“先准备好图鉴素材文件夹，让程序自动生成 JSON”，再在网页里选择要拼的对象。

## 使用场景

1. 用户先把所有宝可梦素材放进一个本地文件夹。
2. 网页读取这个文件夹，显示成图鉴列表。
3. 系统先自动解析图片，生成每个宝可梦的 JSON 数据。
4. 用户浏览、搜索、勾选一个或多个宝可梦。
5. 系统根据所选条目的配色数据，汇总每个色号的总数量。
6. 用户复制或导出结果，用来备料和拼豆采购。

## 范围

### 本期要做

- 本地文件夹导入。
- 从图片自动生成 JSON。
- 图鉴式卡片展示。
- 按名称、编号、属性或关键词筛选。
- 多选勾选。
- 汇总所选宝可梦的色号和数量。
- 显示总豆数、色号清单、重复色号合并结果。

### 本期不做

- 不做通用的“从任意图片自动识别宝可梦并完全理解所有版式”。
- 不做复杂的在线账号系统。
- 不做云端同步。
- 不做自动下单。

## 关键假设

1. 素材是本地文件夹内的一组图片或条目文件。
2. 每个条目最好有稳定的编号或文件名，便于排序和查找。
3. 每个条目最终都要能输出一份结构化 JSON，用于描述拼豆色号和数量。
4. 图鉴图片模板尽量统一，这样自动解析的成功率会更高。

## 推荐实现方式

推荐采用“图片自动解析 + 结构化 JSON + 图鉴列表渲染”的方式。

原因如下：

- 你的核心需求是筛选、汇总和自动出 JSON。
- 图片解析结果落成 JSON 后，后续勾选和汇总就会很稳定。
- 后续如果想增加 OCR 或图片识别，只需要在解析层扩展，不用重写主流程。

## 数据组织方式

建议每个宝可梦条目都包含三类信息：

1. 基本信息：编号、名称、图片路径、标签。
2. 展示信息：封面图、分类、世代、属性等。
3. 拼豆信息：色号到数量的映射。

### 推荐的数据文件格式

优先使用 JSON 作为最终输出格式，CSV 只适合作为人工校对或批量维护的中间格式。JSON 更适合嵌套色号明细。

一个条目可长这样：

```json
{
  "id": 1,
  "name": "妙蛙种子",
  "image": "001-妙蛙种子.png",
  "tags": ["草", "毒", "关都"],
  "beads": [
    { "code": "B3", "count": 42 },
    { "code": "B8", "count": 66 },
    { "code": "H7", "count": 58 }
  ]
}
```

## 自动生成 JSON 流程

1. 用户把一批图片放进固定文件夹。
2. 系统扫描图片并识别图鉴条目。
3. 系统识别图中的编号、名称、色号区域和数量信息。
4. 系统把每个条目写成 JSON。
5. 系统把所有 JSON 合并成可供图鉴页面读取的索引。

## 图片到 JSON 的解析流程

### 1. 输入层

- 读取本地 `image` 文件夹中的图片。
- 按文件名排序，例如 `0001.jpg`、`0002.jpg`。
- 先判断图片是否属于支持的模板家族。

### 2. 版式定位层

- 找到整张图的主内容区域。
- 识别顶部标题区、中央网格区、底部汇总区。
- 自动推导网格行数、列数和单格尺寸。
- 不把坐标写死到某个固定像素值。

### 3. 单格识别层

- 对网格内每个有效格子做裁切。
- 对裁切结果执行 OCR。
- 识别格子中的色号文本，例如 `B3`、`H7`、`F19`。
- 忽略空白格和边界装饰格。

### 4. 汇总校验层

- 按色号统计网格识别结果。
- 读取图片底部的汇总条。
- 对比两份结果的色号集合和数量。
- 一致则自动通过，不一致则标记人工介入。

### 5. 输出层

- 为每张图生成一份 JSON。
- 再生成一个总索引 JSON，供网页读取。
- 生成失败的图片单独输出错误报告。

## 解析模块拆分

为了便于开发，建议把解析器拆成以下模块：

1. `scanner`：扫描文件夹、读取图片列表。
2. `template-detector`：判断图片属于哪种模板。
3. `layout-locator`：定位标题区、网格区、汇总区。
4. `grid-reader`：逐格 OCR 并统计色号。
5. `summary-parser`：读取下方汇总条。
6. `reconciler`：对比两份结果并决定是否自动通过。
7. `json-writer`：输出条目 JSON 和索引 JSON。

## 建议的 JSON 输出格式

每张图输出一份条目 JSON，建议字段如下：

```json
{
  "id": "0001",
  "name": "妙蛙种子",
  "image": "image/0001.jpg",
  "template": "grid-20x19",
  "grid": {
    "rows": 19,
    "cols": 20
  },
  "beads": [
    { "code": "B3", "count": 42 },
    { "code": "B8", "count": 66 },
    { "code": "B15", "count": 35 },
    { "code": "B25", "count": 21 },
    { "code": "F4", "count": 1 },
    { "code": "F19", "count": 1 },
    { "code": "H2", "count": 5 },
    { "code": "H3", "count": 1 },
    { "code": "H6", "count": 21 },
    { "code": "H7", "count": 58 }
  ],
  "total": 251,
  "confidence": 0.98,
  "status": "ok",
  "warnings": []
}
```

## 生成失败时的状态

- `status: ok`：格子统计和汇总条完全一致。
- `status: review`：两份结果不一致，需要人工介入。
- `status: error`：模板识别失败、OCR 失败或图片损坏。

当 `status: review` 时，系统除了保留原始图片和自动识别结果外，还要额外输出一份差异报告，方便人工快速修正。

## 人工介入边界

人工介入只发生在以下情况：

1. 网格统计结果与底部汇总结果不一致。
2. OCR 连续识别失败。
3. 模板检测失败。
4. 图片被裁切、模糊或缺失关键区域。

人工介入时只需要修正差异项，不需要重做整张图。

## 差异报告内容

当图片被标记为 `review` 时，建议输出以下内容：

1. 原始图片路径。
2. 网格统计结果。
3. 底部汇总结果。
4. 两者差异列表。
5. 建议修正项。

差异报告可以是单独的 JSON，也可以是网页里的一块校正面板。

## 人工校正输出

人工校正完成后，系统只更新差异部分，不重算整张图的其他已确认部分。校正结果应写回到最终 JSON，并保留原始自动识别结果，方便追踪。

建议最终 JSON 至少多保留这些字段：

- `reviewed`: 是否经过人工校正。
- `reviewedBy`: 校正人。
- `reviewedAt`: 校正时间。
- `diffs`: 校正前后的差异记录。
- `source`: 原始识别来源和版本号。

## 页面结构

### 1. 图鉴首页

- 顶部：搜索框、筛选器、批量操作按钮。
- 中间：宝可梦卡片网格。
- 每张卡片显示：图片、编号、名称、标签、勾选框。
- 底部或侧边：已选数量、汇总入口。

### 2. 汇总面板

- 展示已勾选的宝可梦列表。
- 按色号合并数量。
- 显示总豆数。
- 支持复制文本结果。
- 支持导出 JSON 或 CSV。

### 3. 数据管理页

- 导入文件夹。
- 检查文件名和数据文件是否匹配。
- 缺失项提示。
- 自动校正识别结果。
- 只有“格子统计结果”和“下方汇总结果”不一致时才进入人工校正。

## 自动校正规则

自动校正的原则不是让人逐格复核，而是让系统做双重校验：

1. 统计网格中每个格子的色号，得到一份自动计数结果。
2. 读取图片下方的汇总条，得到另一份总计结果。
3. 如果两者在色号集合和数量上完全一致，则自动判定该条目有效。
4. 如果两者不一致，则标记为需人工介入。
5. 人工只处理不一致的条目，不处理已经自洽的条目。

这个规则的目标是把人工工作量压到最低，只把注意力放在真正有问题的图片上。

## 核心流程

1. 用户导入本地文件夹。
2. 系统扫描图片并自动生成 JSON。
3. 图鉴页面渲染卡片列表。
4. 用户搜索、筛选、勾选。
5. 系统实时计算汇总。
6. 用户复制或导出结果。

## 汇总规则

- 同一个色号在多个宝可梦里出现时要合并。
- 数量按条目中的 `count` 累加。
- 总豆数为所有色号数量之和。
- 如果同一个宝可梦重复勾选，默认只算一次。

## 材料清单

### 必需材料

- 宝可梦图鉴图片文件夹。
- 每个条目的编号和名称规则。
- 图鉴图片中固定的网格和色号文字样式。
- 色号字典，例如 B3、B8、H7 对应的颜色名称或色块。

### 建议材料

- 统一尺寸的封面图。
- 条目标签，如属性、世代、颜色主题、难度。
- 少量已标注的样例图，用来验证自动识别准确率。

### 如果要加自动识别

- 固定模板样本图。
- OCR 或图像识别库。
- 色块定位规则。
- 人工校对入口。

## 技术建议

### 前端

- 适合用 React、Vue 或纯前端静态页面。
- 如果优先简单和快速，可先做纯前端单页应用。

### 数据层

- 先把自动识别结果落成本地 JSON 文件最稳。
- 如果数据量继续增大，再迁移到 SQLite 或 IndexedDB。

### 识别层

- 第一阶段做 OCR + 版式定位，先输出可用 JSON。
- 第二阶段增加基于“格子统计 vs 下方汇总”的自动校正。
- 第三阶段再优化模板图像解析和识别准确率。

## 风险与对策

### 风险 1：条目数据不统一

对策：先定统一 JSON 结构、文件命名规则和图片模板约束。

### 风险 2：图像模板不一致

对策：优先保证图鉴素材版式统一，再考虑增强识别。

### 风险 3：色号口径不一致

对策：提前建立色号字典和统计规则，避免不同条目使用不同计数方式。

### 风险 4：格子统计与下方汇总不一致

对策：把不一致条目标记为人工校正对象，其余条目自动通过。

## 建议的开发顺序

1. 先做图片输入、OCR 解析和样例 JSON 输出。
2. 再做图鉴卡片展示和勾选。
3. 再做色号汇总逻辑。
4. 再做复制和导出。
5. 再优化识别准确率和手动校正流程。

## 建议项目结构

建议把项目拆成三部分，减少互相耦合：

```text
pixel/
├─ image/                # 原始图片输入
├─ output/               # 解析生成的 JSON 和差异报告
├─ src/
│  ├─ parser/            # 图片到 JSON 的解析器
│  ├─ viewer/            # 图鉴展示和勾选页面
│  └─ shared/            # 公共类型和汇总逻辑
└─ docs/
  └─ superpowers/
    └─ specs/          # 设计说明
```

## 第一版实现边界

第一版只做最小可行闭环：

1. 读取 `image` 文件夹中的样例图。
2. 自动输出每张图的 JSON。
3. 对 `ok` 和 `review` 状态做区分。
4. 用网页读取 JSON 并支持勾选。
5. 输出汇总结果。

第一版不追求所有模板都支持，也不追求完全零误差。目标是先让整条链路跑通。

## 第一版脚本分工

建议先写三个脚本或命令入口：

1. `parse-images`：批量把图片转成 JSON。
2. `build-index`：把所有条目 JSON 聚合成索引。
3. `serve-viewer`：启动图鉴页面预览和汇总。

## 第一版验收

第一版只要满足下面几点就算完成：

- 能处理 `image` 文件夹里的样例图。
- 能生成每张图的条目 JSON。
- 能输出 `ok`、`review`、`error` 三种状态。
- 能在网页里选图并汇总色号数量。
- 能导出最终汇总结果。

## 验收标准

- 能从本地文件夹读取图片并自动生成条目 JSON。
- 能在页面上看到图鉴列表。
- 能勾选多个宝可梦。
- 能正确合并重复色号并输出总数量。
- 能导出或复制汇总结果。
